# 편집·쇼츠·전달 검토

제목과 내용의 불일치, 쇼츠 음성 절단 누락, 시각적 혼동, 업로드 상태 오판을
제작 단계에서 발견하기 위한 에이전트 지침이다. 본편의 QA 통과가 쇼츠와 외부
게시까지 보증하지 않는다. 사용자 승인을 새로 추가하지 않고 기존 대본·프리뷰·
초본 승인 절차 안에서 수행한다.

## 적용 시점과 기록

[검토 양식](../agent/templates/release-review.md)을 실행 폴더의
`release-review.md`로 복사한다. `통과 / 수정 필요 / 미검토 / 해당 없음`과 근거를
적는다. 해당 없음을 선택할 때도 이유를 쓴다. 입력이나 산출물이 바뀌면 영향을
받는 항목을 다시 검토한다. 검사하지 않은 항목을 통과로 채우지 않는다.

| 시점 | 확인할 대상 | 남길 근거 |
| --- | --- | --- |
| 대본 승인 요청 전 | 본편 및 선택된 쇼츠 나레이션 | 제목의 질문, 답 인용/씬, 필수 전제, 마무리, 길이 목표 |
| 제목·설명·포함 장면 변경 후 | 실제 적용될 각 언어 제목과 나레이션 | override를 포함한 제목, 빠진 답/전제 여부, 재검토 범위 |
| 프리뷰·초본 검토 | 시각 표현과 움직임 | 물리량별 표현, 절개·복원·접합부 전중후 프레임/클립 |
| 음성 생성 후·프리뷰 전 | 실제 MP3의 미지정 쉼·계획한 쉼 | 적용된 voice-pause-gate의 현재 해시, 문장·시점, 청취 항목과의 구별 |
| 쇼츠 생성 후 | 실제 각 언어 MP4와 번인 자막 | 해시, 원본/출력 시간 대응, 음성 내용·타이밍 검사 결과 |
| 외부 게시 전 | 검증된 파일과 업로드 문구 | 동일 파일 해시, 최종 제목, 출처·라이선스, 업로드 대상 |
| 게시 후 | 실제 서비스의 영상·추가 오디오 | 영상/채널 ID, URL, 조회 값, 저장 후 오디오 열의 상태 |

**구현 범위:** 이 문서와 `release-review.md`는 에이전트의 검토 계약이다.
현재 `story-chain.json`, `subtitle-gate`, 미디어 QA 등에 이 검토가 모두 자동으로
연결된 것은 아니다. 기존 자동 게이트의 성공을 아래 의미·싱크 검사의 성공으로
바꿔 부르지 않는다. 아직 없는 CLI 옵션·검사 명령·JSON 스키마를 만들어 설명하지 않는다.

## 1. 제목의 질문을 실제 대본이 해결하는가

1. 본편과 쇼츠 각각 제목이 시청자에게 약속하는 질문을 한 문장으로 쓴다.
   질문형이 아닌 제목도 시청자가 알게 될 사실을 적는다.
2. 그 답을 실제 나레이션에서 인용하고 씬 번호를 붙인다. 핵심 단어의 등장이나
   관련 주제 설명만으로 통과시키지 않는다. `왜 북쪽인가`와 `자기장이 어디서
   생기는가`처럼 가까운 질문도 구분한다.
3. 쇼츠는 `in_shorts: true`인 장면만 순서대로 이어 읽는다. 제외한 장면에만
   있는 답, 용어 정의, 원인, 조건, 대명사의 지시 대상에 의존하면 수정 필요다.
   마지막 문장이 남긴 질문을 닫는지도 확인한다.
4. `story-review.md`에 본편과 함께 선택된 쇼츠 전체 나레이션을 제시한다.
   본편에서 쇼츠 표시를 찾아 조합해야만 검토할 수 있는 상태로 끝내지 않는다.
5. 제목을 바꿀 때는 적용 우선순위(대본/번역 → `upload-overrides.json` → 명시적
   명령 인자)를 확인하고 최종 문구를 검토한다. 번인 제목, `upload.md`, 실제
   업로드 제목이 같아야 한다. 언어별 번역도 같은 질문과 강도의 주장을 담는다.

**예:** `나침반은 왜 북쪽을 가리킬까?`로 바꾸었는데 나침반의 방향을 설명하는
장면을 쇼츠에서 제외했다면 제목 변경 작업도 아직 끝난 것이 아니다. 북쪽이라는
단어가 없다는 사실은 점검 신호이며, 단어를 끼워 넣는 것으로 해결하지 않는다.

제목·설명만 고쳐도 기존 나레이션이 충분히 답하면 override를 쓰고 해당 쇼츠와
문구만 갱신한다. 승인된 `script.json`과 `translations.json`을 제목 때문에 다시
쓰지 않는다. 답이 부족해 나레이션이나 `in_shorts`를 바꾸려면 변경된 전체 대본과
쇼츠 구성을 보여주고 기존 대본 승인 절차를 따른다. 해시를 조작해 승인을 재사용하지 않는다.

## 2. 설명의 밀도와 쇼츠의 독립성

- 본편과 쇼츠의 중심 질문·길이 목표를 따로 적는다. 사용자 목표와 현재 설정을
  우선한다. 60~90초를 간결한 설명의 검토 후보로 삼을 수 있으나 고정 제한으로
  강제하지 않는다. 더 긴 쇼츠는 어떤 설명 때문에 그 길이가 필요한지 쓴다.
- 각 장면이 더하는 정보와 앞뒤 연결을 한 문장으로 설명한다. 같은 결론을
  반복하는 장면, 본편에만 필요한 세부 분류, 질문과 무관한 우주/역사/응용 부연은
  제외 후보로 둔다. 필요한 전제를 먼저 자르고 반복 문장을 남기지 않는다.
- `알맞은`, `복잡한`, `작용한다` 같은 표현이 핵심 원인을 숨기지 않는지 확인한다.
  대상 → 변화/작용 → 결과를 말이나 화면에서 구체적으로 보여준다. 예를 들어
  전류가 자기장을 만든다는 문장의 반복만으로 자기장이 유지되는 원리를 설명했다고
  하지 않는다. 에너지 공급과 손실 보충이 필요한 경우 둘의 역할도 구별한다.
- 질문 뒤에 그 질문의 답이 오는지, 말한 인과관계가 화면의 순서와 맞는지 확인한다.
  과학적 예외와 단순화는 필요한 최소한으로 남긴다. 속도를 올려 정보 과밀을 덮지 않는다.

## 3. 화면이 같은 물리 과정을 설명하는가

- 물리량별로 색·모양·진행 방식의 대응을 계획에 적는다. 유체 흐름, 전류,
  자기장, 힘을 같은 선처럼 표현하지 않는다. 색만으로 구분하기 어려울 때는
  순차 등장·강조·경로 형태로 보완하고 현재 `text_policy`를 지킨다.
- 전체/내부, 절개/복원, 불투명/투명 상태를 명시한다. 경계의 단일 프레임뿐
  아니라 실제 클립의 전·중·후에서 이중 표면, 갑작스러운 닫힘, 중복 객체,
  순간 이동과 깜박임을 확인한다. 상태 지문 통과가 시각적 정상의 증명은 아니다.
- 본편에서 연속이던 장면도 쇼츠에서 중간 장면을 빼면 새 경계가 생긴다.
  모든 새 접합부에서 대상의 상태와 나레이션 연결을 다시 검토한다.
- 세로 출력의 실제 설명 영역에서 핵심 대상과 경로를 확인한다. 제목·자막이
  크더라도 그림이 작아 원인과 결과를 읽을 수 없으면 수정 필요다. 확대/재배치가
  필요한지 검토하며 물리적으로 필요한 주변 구조를 임의로 잘라내지 않는다.

## 4. 최종 쇼츠의 음성·자막 검사

쇼츠를 만들 때 [화면 배치](shorts-safe-area.md)의 상자와 글자 실측 검사를
적용한다. 실제 모든 언어 MP4의 제목·자막·핵심 객체를 확인하고, 실기기 검사
여부를 구분해 기록한다.

### 하나의 편집 시간표

유지 구간을 원본 타임라인의 반열림 구간 `[start, end)`로 기록한다. 원본 FPS,
구간, 배속, 언어별 음성 소스와 MP4/자막 해시를 남긴다. 구간 i 안의 원본 시점 t가
출력에서 나타날 위치는 `(앞서 유지한 구간 길이 합 + t - start_i) / 배속`이다.
영상, 음성, 자막에 이 대응을 같이 적용한다. 계획의 구간과 인코딩 결과를 모두 본다.

### 실제 출력 확인

1. 각 언어의 **인코딩된 쇼츠 MP4에서 디코딩한 음성**을 검사한다. 길이가 맞거나
   `ffmpeg`가 성공했다고 음성이 잘렸다고 가정하지 않는다. `-shortest`가 긴
   잘못된 음성의 끝을 잘라 길이만 맞춘 경우도 찾아야 한다.
2. 시작과 끝, 모든 삭제 구간의 접합부 앞뒤에서 해당 장면의 실제 발화·자막·
   화면을 대조한다. 경계 전후 약 2초를 출발점으로 삼고, 무음이면 인접한 발화까지
   넓힌다. 마지막 문장 잘림, 제외한 대사 잔존, 문장 반복, 누적 밀림은 실패다.
3. 승인된 원본 음성에서 유지 구간을 **독립적으로** 잘라 이어 붙인 기준과
   완성 MP4 음성을 비교한다. 제작 필터를 그대로 재사용해 기대값을 만들지 않는다.
   파형 비교는 음성 있는 구간을 쓰며 배경음악·무음만 일치한 결과를 채택하지 않는다.
   언어별 발화/자막 내용 검토나 전사를 함께 사용하고, ASR을 청취라고 기록하지 않는다.
4. 원본 대비 일정한 오프셋과 시간에 따라 늘어나는 밀림을 구별한다. 검토 구간·
   측정 오차·판정 기준을 기록한다. 100ms를 넘는 설명되지 않은 지연, 잘못된 문장,
   경계의 음절 손실은 수정 대상으로 삼고, 그 이하도 실제로 어긋나면 통과시키지 않는다.
   파형 정렬 통과는 기존 자막 큐의 문장 타이밍까지 자동 보증하지 않는다.
5. FFmpeg 버전이나 편집 필터가 바뀌었거나 절단 이상이 보이면, 서로 다른 세
   신호에서 가운데 구간을 빼는 작은 재현으로 실제 절단을 확인한다. 의도적으로
   잘못 자른 음성도 검사에 넣어 실패하는지 확인한다. 명령 문자열 검사만으로 끝내지 않는다.

2026-10-11 실행에서는 설치된 FFmpeg에서 `aselect`가 기대한 음성 구간을 제거하지
않았고 `atrim`으로 각 구간을 자른 뒤 `concat`하는 실행별 수정으로 해결했다.
이를 모든 FFmpeg 버전의 결함으로 일반화하지 않는다. 공용 `shorts.py`가 고쳐졌다고
가정하지 말고 현재 구현과 실제 출력을 확인한다. 재현·수정·검증 코드는 해당 run의
`scripts/`, 중간물은 `.render-cache/`에 둔다.

싱크 실패만으로 TTS나 3D 본편을 재생성하지 않는다. 컷·PTS·배속·큐 이동을 먼저
확인한다. 원본 음성 내용 자체가 틀렸을 때만 그 원인에 맞는 대본/음성 절차로 돌아간다.

## 5. 자산 출처는 첫 프리뷰 전에 확보한다

GLB의 `asset.extras`와 배포 페이지를 확인하고 실행의 `assets/CREDITS.md`에
파일명·저작자·모델 원문 URL·이용 조건 URL·변형 여부를 적는다. 이름이 `sun.glb`이거나
사용자가 기관명을 알려줬다는 이유만으로 특정 라이선스를 추정하지 않는다.
공식 원본을 찾고 로컬 모델과의 대응 근거를 남긴다. NASA 자료에도 확인한 NASA
이용 지침을 표기하며 임의의 CC 라이선스를 붙이지 않는다. 업로드 문구의 출처 경고는
숨기지 말고 실제 근거로 해결한다.

최종 렌더 뒤 출처만 보완할 때는 승인된 소스 사본과 기존 산출물을 보존한다.
GLB 메타데이터 변경도 파일/소스 해시를 바꾼다. 시각 데이터가 같은지 증명한
기록을 별도로 남기고, 승인 해시를 덮어쓰거나 새 렌더에 과거 승인을 쓰지 않는다.
출처 수정으로 본편 재렌더가 필요한지와 업로드 문구 갱신만 필요한지를 구분한다.

## 6. 자동 전달과 검토 순서를 맞춘다

현재 CLI의 `produce --quality final`은 본편 제작 뒤 `_after_final()`에서
쇼츠·문구·로컬 전달을 연속 실행한다. 쇼츠에 대한 수동 검토를 기다리는 기능이나
`--skip-delivery` 옵션은 현재 없다. 자동 업로드가 켜져 있는데 나중에 검사하겠다는
계획으로 이 명령을 실행하지 않는다.

추가 검사가 공용 자동 게이트에 연결되기 전에는, 자동 전달을 사용하는 실행의
`runs/<run>/scripts/`에 단계별 실행 코드를 둔다. 기존 `video_harness.pipeline.produce`
함수로 승인·본편 QA를 그대로 수행하고, 쇼츠 생성 → 위 실제 출력 검사 → 검토한
해시 확인 → 업로드 문구 생성/검사 → 기존 전달 훅 순서로 이어간다. 이 함수와 CLI의
후처리가 분리되어 있는지 현재 코드를 먼저 확인한다. 기존의 자동 게이트나 사용자
승인을 우회하는 자체 렌더러·업로더를 만들지 않는다. 새 명령이 이미 구현돼 있다고
보고하지 않는다. 사용자 업로드 설정을 임의로 바꾸는 방식으로 해결하지 않는다.

검사가 실패하면 외부 전달만 보류하고 완성된 본편과 이전 정상 쇼츠를 보존한다.
영향받은 후처리를 수정·검증한 뒤 기존 전달 경로로 재개한다. 이미 게시한 ID가
있으면 상태와 해시를 확인하고, 새 파일을 조용히 중복 게시하거나 이전 영상을 삭제하지 않는다.

## 7. 브라우저 실패와 실제 권한 거부를 구별한다

1. 대상 사이트·채널·영상 ID와 업로드할 파일 경로/해시를 확인한다. 기존 사용자
   허가는 유지하며 동일 작업에 다시 승인을 묻지 않는다.
2. 제공된 파일 업로드 도구와 해당 브라우저의 안내를 먼저 따른다. 오류 문구와
   실패 단계를 기록한다. 자동 파일 선택의 확장 프로그램 오류, OS 파일 접근
   거부, 사이트 업로드 거부, 로그인 만료, 서버 처리 대기를 구분한다.
3. 자동 선택기만 실패했고 도구가 일반 파일 선택창을 허용하면 같은 `cua_repl`로
   OS 선택창을 사용한다. macOS에서는 실제 창이 열린 것을 확인하고 경로 이동으로
   승인된 파일을 고른다. 파일명·언어를 확인한 뒤 전송하며 이전 UI 인덱스를 추측하지 않는다.
4. 실제 파일 접근 거부나 사이트 권한 거부를 다른 경로로 우회하지 않는다.
   보안 설정 확대, 인증, 사용자 조작이 필요하면 어떤 권한이 어느 단계에 필요한지
   설명한다. 도구가 요구하는 사용자 안내도 그대로 제공한다. 단순한 도구 오류를
   사용자 전체 브라우저 권한이 없다는 뜻으로 말하지 않는다.

### Studio 추가 음성의 완료 기준

- `studio-audio-job.json`과 `delivery-manifest.json`의 영상/채널/원본 해시를
  대조하고, 각 M4A 해시를 확인한다. 현재 채널과 한국어 본편 제목도 화면에서 확인한다.
- 기존 언어의 오디오가 비어 있는지 먼저 본다. 출처 모를 기존 게시/처리 중
  트랙을 덮어쓰지 않는다. 이번 작업에서 직접 전송한 동일 해시만 재시도 기록으로 인정한다.
- 언어 → 오디오 추가 → 파일 선택 → **게시** → 상위 언어 세부정보의
  **업데이트/저장**을 확인한다. 버튼 이름은 실제 UI를 따른다. 하위 창을 닫은
  직후의 `게시됨` 표시만으로 최종 저장이 끝났다고 판단하지 않는다.
- 최종 저장 후 언어 목록을 다시 읽는다. **오디오 열**의 `게시됨`을 언어별로
  확인하고 URL·확인 시각·파일 해시·화면/DOM 근거를 기록한다. 제목·설명 열의
  `게시됨`, `처리 중`, `95%`, 업로드 성공 메시지는 이 기준을 대신하지 않는다.
- 전송 후 처리 중이면 작업 파일에 `processing`과 마지막 확인 상태를 남긴다.
  같은 파일을 다시 전송하지 않는다. 다른 작업을 진행한 뒤 다시 확인하고,
  외부 처리 대기가 길어지면 Studio 화면과 재개 기록을 유지한 채 정확한 상태를
  전달한다. 무인 CLI가 브라우저를 확인할 것처럼 약속하지 않는다.
- 모든 오디오의 실제 게시와 API 영상 항목의 성공이 확인될 때만 전체 전달을
  `complete`로 기록한다. 그 전에는 `delivery-report.status=awaiting_studio_audio`다.

### API 응답에서 설정 값이 빠질 때

합성 콘텐츠 표시 등 조회 값의 **누락**과 요청과 **다른 값**을 구분한다.
누락 값을 `true`로 채우거나 검사를 없애지 않는다. 동일 영상의 Studio에서 실제
설정을 확인할 수 있으면 API 값은 그대로 보존하고, 별도 Studio 확인 값·ID·
산출물/메타데이터 지문·시각·근거를 남긴다. 그 증거를 지원하는 검증 경로로만
재개하며, 현재 업로더가 이를 자동 지원한다고 가정하지 않는다. 불일치 값이
실제로 남아 있으면 해결 후 재검사한다. 확인 실패를 재업로드로 해결하지 않는다.
